# Rubric: is this plan ready to post and build from?

Every check reads the candidate plan and plan comment against the issue, its thread, and the repro evidence the plan builds on. Grade the plan itself; length, polish, and confidence of tone are never evidence for a pass. references/evidence-guide.md says where each check's evidence lives, and procedure.md says when and how to gather it.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| cause-grounded | The plan's stated diagnosis read against every step, control run, and measurement in the repro-evidence block (Diagnosis and grounding family) | The stated cause explains the behavior the repro evidence shows AND is consistent with every control run and measurement in the package. Fails when any control or measurement in the package rules the stated cause out (the same failure happens without the blamed component, the blamed step takes no time in the timing data, the blamed module demonstrably works in the same build), when the plan adopts a diagnosis from the thread that the package's own evidence contradicts, or when the plan states no cause at all. A cause that agrees with a maintainer's confirmed diagnosis and with every control passes. | required |
| bounded-scope | The plan's scope statement, approach steps, and named files read against what the issue reports (Scope family) | Everything the plan commits to building is needed to fix the reported behavior. Work outside that is either absent or explicitly deferred or marked not in scope. Fails when the plan bundles in work the issue never asked for: refactors or rewrites beyond the fix site, migrations or dependency upgrades, new options, settings, or UI, new frameworks, or CI and test-harness changes unrelated to proving the fix. Deferring part of the problem with a stated reason passes; a narrower fix is not a scope failure. | required |
| executable | The plan's approach, named files or modules, and order of work (Executability family) | A stranger could start building today without asking the author anything: the plan names one chosen approach and at least the file, module, or component where the change lands. Exact function names may be pinned later when the plan says how they will be found. Fails when the plan names no files or areas, leaves the core decision open ("X or Y, whichever is easier", "somewhere in the stack", "not sure which layer"), or describes investigation in place of a change. | required |
| test-decisive | The plan's test plan read against the repro evidence's steps and expected/actual (Test plan family) | The test plan names an observable outcome that would differ between the broken and fixed code: the repro re-run with its expected result stated, a specific assertion, a regression test reproducing the issue's case, or a named measurement with a target. Fails when the only test is generic ("run the full test suite", "CI passes", "nothing else breaks") or subjective ("should feel fast"), or when no outcome tied to the reported behavior is named. | required |
| thread-engaged | The plan comment and plan read against maintainer and owner direction in the thread highlights, plus prior-art PRs or patches named there (Comms family) | Where a maintainer, owner, or collaborator has given explicit direction in the thread (isolated a culprit, posted a patch or test binary, named a preferred approach, linked an open or prior PR, asked a question of contributors), the plan or comment engages it: follows it, builds on it, or names it and says why it departs. Passes when the thread holds no such direction. Fails when the comment proposes a different direction as if that maintainer signal did not exist. | required |
| ai-policy-met | The repo-facts contribution policy line read against the plan comment (Comms family) | Treat every package as AI-assisted work. If the repo's stated policy requires disclosing AI use in issues or comments, or disclosing all AI usage in any form, the plan comment discloses the tool and the extent of the help. Passes when the repo states no AI policy, when the policy requires disclosure only in pull requests, or when it asks only for human understanding or human-written comments and the comment reads as the writer's own specific words. | required |
| comment-specific | The plan comment read against the plan and the issue (Comms family) | The comment states the chosen approach in terms specific to this issue and points at the writer's own evidence. Fails on a piggyback ("same approach as above"), boilerplate that fits any issue, or a comment with no approach. | required |
| unknowns-named | The plan's risks, unknowns, and deferrals (Honesty family) | The plan names at least one risk, unknown, or deferral, and states uncertainty where the evidence leaves it open. | preferred |
| no-promised-dates | The plan comment (Comms family) | The comment commits to no delivery date or timeline. | preferred |

## Verdict rule

accept when every required check grades pass. reject when any required check grades fail or unclear: unclear counts as fail, because a plan that cannot be verified from the package is not ready to build from. Preferred checks are reported and never change the verdict.
